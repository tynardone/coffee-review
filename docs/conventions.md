# Conventions

How code in this project is organized and named. Decided once here so it isn't
re-decided in every change. If a rule stops fitting, change it here first, with a
[decision record](decisions/) if the reason isn't obvious.

## Packages

```
src/coffee_review/
  cli.py               Typer app: parses arguments, calls pipeline functions. No logic.
  config.py            Settings only.
  logging_setup.py     Terminal + run-log logging for CLI runs. Used by cli only.
  progress_display.py  The Rich progress bar. Used by cli only.
  models/              pydantic models: the contracts between stages.
    common.py          Slugs, UTC datetimes, the frozen base, formatting helpers.
    scrape.py          Sitemap entries, manifest rows, scrape summaries.
    parsed.py          Parsed review records and parse issues.
    clean.py           The clean-table contract (pandera) and cleaning-rule names.
    economic.py        Exchange-rate and CPI rows and the economic-table contracts.
    frames.py          Checks shared by the pandera contracts.
  clients/             Talk to the outside world over HTTP. Return raw text/JSON.
    economic.py        Telling an economic-data source's answer from a refusal.
  storage/             Read and write each data layer on disk. Know paths and formats.
  parsers/             Pure functions: raw HTML/XML/JSON in, models out. No I/O.
  transforms/          Pure functions on tables: clean, convert, adjust.
    rules.py           raw_<field> / _rule_<field> columns, the cleaning log.
    dates.py, scores.py, roast.py, places.py, roasters.py, price.py, units.py,
    lots.py, text.py
                       One module per field family.
    economic.py        What FX days and CPI years to fetch; build the economic tables.
    lookup_tables.py   Loads the CSVs in lookups/ (the one file access allowed).
    lookups/           Hand-kept and generated lookup tables, versioned with code.
  pipeline/            One module per stage: wires clients + storage + parsers/transforms.
    progress.py        The progress Protocol a stage reports through (no display code).
```

Every package has an `__init__.py`, including those under `tests/`. Import from
the module that defines a name (`coffee_review.models.scrape`), not from a
package that re-exports it.

### The dependency rule

Drawn, with the data flow, in [architecture.md](architecture.md); checked on
every commit and in CI by import-linter (`uv run lint-imports`).

```
cli → pipeline → {clients, storage, parsers, transforms} → {models, config}
cli → {logging_setup, progress_display}
```

Imports only point along the arrows. Nothing imports `cli` or `pipeline`.
Display and logging setup are the CLI's concern: a pipeline reports progress
through `pipeline/progress.py`'s Protocol and logs with `logging`, never
knowing how either is shown.
`parsers` and `transforms` import no I/O at all (no `httpx`, no file access),
except that `transforms/lookup_tables.py` reads its own CSVs with
`importlib.resources`: they're code, not pipeline data.
That's what lets them be tested with plain inputs, and what stops one stage
reaching into another.

**Only `storage/` knows data formats and paths.** Everything else holds a
storage Protocol (`RawStore`, …) and talks in project terms: slugs, models,
datetimes, strings. One factory (`open_raw_store`) picks the implementation, so
swapping storage is a change in one place ([ADR 0006](decisions/0006-sqlite-manifest-and-storage-boundary.md)).

When it's unclear where new code goes, ask what it *does*:

| It... | It goes in |
|-------|-----------|
| makes an HTTP request | `clients/` |
| reads or writes a file under `data/` | `storage/` |
| talks to the manifest or saved pages | `storage/` (through a Protocol) |
| decides which reviews to fetch | `pipeline/fetch_rules.py` (pure) |
| decides which FX days or CPI years to fetch | `transforms/economic.py` (pure) |
| turns raw HTML/XML into a model | `parsers/` |
| turns one table into another | `transforms/` |
| runs a stage from start to finish | `pipeline/` |
| reads command-line arguments | `cli.py` |

### Clean-stage transforms

Each transform is `LazyFrame → LazyFrame`. It reads `raw_<field>` (the pipeline
renames parsed fields so clean columns can reuse their names), adds typed
columns, and adds `_rule_<field>`: the list of `CleanRule`s it applied to that
row. Every value that becomes null must have a rule; the pipeline checks.
A lookup table gains a row when the clean report lists a real place, currency
or unit it doesn't know, never to make a doubtful value pass. The ISO lists are
generated by `scripts/generate_lookup_tables.py`, never edited by hand.

## Data layers

Each stage reads one layer and writes the next. These names are used the same
way in paths, module names and CLI commands.

| Layer | Path | Written by |
|-------|------|-----------|
| raw | `data/raw/` | scrape (pages, manifest); fx, cpi (`fx/`, `cpi/` responses) |
| parsed | `data/parsed/` | parse |
| clean | `data/clean/` | clean |
| economic | `data/economic/` | fx, cpi |
| final | `data/final/` | enrich |

`data/` is never committed.

## Naming

- **Modules are nouns** for what they hold: `review_store.py`, `forex_api.py`.
- **Functions are verbs** for what they do: `fetch_sitemap`, `parse_review`,
  `normalize_price`.
- **One name per concept**, everywhere: *review*, *slug*, *lastmod*, *delisted*.
  Don't alias (no `article` for a review, no `modified` for lastmod).
- **Names say what we observe, not what we assume.** A review missing from the
  sitemap is *delisted*, not "removed" or "deleted": we can't see why it's gone,
  and "removed" reads like we deleted it ourselves.
- **Classes only where there's state to hold**: HTTP clients, stores. Parsing and
  transforming are plain functions.
- **Leading underscore** for module-private helpers (`_parse_retry_after`). Other
  modules may not import them; tests should rarely need to (see
  [Tests](#tests)).
- **Errors end in `Error`** and say what to do: `MissingApiKeyError` names the
  env var to set.

## Docstrings

Google style, for every public module, class, function and method in `src/`.
Ruff checks that they exist and are well formed (`pydocstyle`, Google
convention); the rest is on us.

- **One-line summary** that stands alone, then a blank line, then any detail.
- **`Args:`** for every function with two or more parameters, or one whose
  meaning isn't obvious. Types come from the hints, so don't repeat them.
- **`Returns:`** when the return value needs explaining; **`Raises:`** for
  every error a caller should expect to handle.
- **`Attributes:`** on result and record classes whose fields aren't obvious
  from their names.
- Simple things stay one line: properties, `close()`, `describe()`.
- **Constructor arguments go on the class** docstring, not `__init__`.
- **An implementation of a Protocol subclasses it and marks its methods
  `@override`**, so the Protocol's docstrings cover them, and mypy checks every
  method really matches.
- **CLI commands are the exception:** a Typer command's docstring is its
  `--help` text and each option documents itself, so they get no `Args:`.
- Code is written with double backticks (``` ``raw_price`` ```), as Sphinx and
  other docs tools expect.

## Tests

### What to test

**Test the public interface, and let private code be covered through it.**
A test of a public function checks behavior we've promised to keep. Private
names are free to change, so a test that reaches into one breaks on a
refactor even when nothing observable changed, and that noise makes people
reluctant to refactor.

1. **Write tests against the public interface first.**
2. **Check coverage** (`uv run pytest --cov`). Private code no public-path test
   reaches is either dead or a sign of a missing test case for a branch of the
   public behavior.
3. **Test a private function directly only when it's complex and awkward to
   reach:** substantial self-contained logic with many edge cases (a tricky
   parser, a date-cutoff rule, a matching rule), or a public path that needs
   files, a database or the network to set up. Characterizing legacy code
   before changing it is the other good reason. Such a test is coupled to an
   implementation detail and may need updating on a refactor; that's the
   accepted cost.
4. **If you keep wanting more direct tests of one private function, promote
   it**: make it public, or give it its own module with a real interface. Then
   testing it directly is no longer an exception, and the dependency is
   explicit.

### How tests are written

- `tests/` mirrors `src/coffee_review/`: `clients/http.py` is tested in
  `tests/clients/test_http.py`.
- Test names read as the behavior: `test_client_error_is_not_retried`, not
  `test_request_2`.
- One behavior per test. If the name needs "and", split it.
- No network in tests. HTTP goes through `httpx.MockTransport`; tests that must
  hit a real service are marked `@pytest.mark.network` and are skipped by default.
- Shared fixtures live in `tests/conftest.py`; saved pages and data files live in
  `tests/fixtures/`, kept small and trimmed to the markup a test needs.
- Write the test first and watch it fail. For code that already exists, break
  the code on purpose once to prove the test catches it.
- **Prefer fakes behind a Protocol over mocks.** A fake is a small working
  implementation (`InMemoryRawStore`, `FakeSite` in `tests/fakes.py`); a mock
  only records calls. Hold a fake to the real thing's contract tests so it
  can't drift.
- Tests may deliberately bypass validation (for example
  `unthrottled_site_settings()` turns the rate limit off); say so in the
  helper's docstring.

## Python version notes

- The project targets Python 3.14, and ruff formats for it. One visible
  result: an `except` catching several exceptions without binding them is
  written without parentheses, `except TypeError, ValueError:` (PEP 758).
  It's correct, not a Python 2 leftover; the formatter writes it that way.
- `type X = ...` aliases (PEP 695) are used for named unions and Literals.

## Working

- One concern per commit. A config fix and a parser change are two commits.
- `docs/roadmap.md` is updated in the same commit as the work it tracks.
- `TODO(<stage>): <what and why>` for known gaps, e.g. `TODO(clean): ...`.
