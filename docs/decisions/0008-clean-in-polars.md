# 0008. The clean stage is Polars, with hand-kept lookup tables

Date: 2026-11-22 · Status: accepted

## Context

The parse stage (M2) keeps every value as the text the page had
([ADR 0007](0007-parse-text-type-later.md)). The clean stage (M3) turns that
text into typed columns: dates, scores, Agtron readings, prices split into
parts, and places as country and region, so the dashboard (M7) and models (M8)
can compare origins and roasters by region.

The project is also a data-engineering portfolio piece, so the layers should
read as a recognisable pattern:

| Layer | Where | What | Built by |
|---|---|---|---|
| Raw (bronze) | `data/raw/` | gzipped HTML + manifest | M1, Python |
| Parsed | `data/parsed/` | one row per review, all text | M2, Python |
| Clean (silver) | `data/clean/` | typed columns + cleaning log | M3, Polars |
| Marts (gold) | later | joined to FX and CPI, dimensions | M5+, dbt revisited |

Three ways to build M3 were weighed: plain Python with a pydantic model per
row, Polars, and dbt-duckdb.

## Decision

- **M3 is Polars**, in the project's Python codebase, tested with pytest and
  hypothesis. Most rules are column expressions; procedural ones (places,
  prices) are pure Python functions applied once per *distinct* value and
  joined back.
- **Interpretation lives in hand-kept lookup tables** in
  `transforms/lookups/` (places, currencies, units), versioned with the code.
  Two complete tables, every ISO country and every ISO currency code, are
  generated by `scripts/generate_lookup_tables.py`, so values no review has
  used yet are still known.
- **Every change is recorded.** Each transform lists the rules it applied in a
  `_rule_<field>` column; the run turns them into `cleaning_log.parquet`, and
  stops (writing nothing) if any value became null without a rule.
- **A contract guards the silver layer.** pandera models (`models/clean.py`)
  state each clean table's columns, types and checks; every run validates both
  tables and the log before writing.
- **New variation is surfaced, not silently absorbed.** Values the lookups
  don't know, and misspellings matched by close spelling, are listed in the
  report's *To review* table, marked **new** against the previous run, and a
  warning is logged when anything is new.
- **dbt waits for M5,** where the work is relational: joins to exchange rates
  and inflation, the final table, dimensions. A field that turns out to need
  SQL-unfriendly parsing there can be a dbt Python model.

## Why

- **The hard part of M3 is messy strings, not relations.** Prices come in 30
  currency spellings and units from `ounces` to `five 5-gram single-serve
  packets`; places in a dozen spellings of Hawaiʻi. In SQL regex this would be
  the least readable part of the project; in Python it's small, tested
  functions.
- **It keeps one codebase and one test style** while the transforms are still
  changing with every new format the report turns up.
- **It's fast enough not to matter:** the whole clean stage runs in under a
  second over 9,440 reviews.
- **It's the common pattern:** Python cleanup to silver Parquet, then dbt for
  the modelled layers, so the portfolio reads like real data work.

## Alternatives considered

- **Plain Python, a pydantic model per row.** Clean and very testable, but it
  reads as a Python app, not a data pipeline, and table-level checks (unique
  slugs, coverage) need a frame anyway.
- **dbt-duckdb for M3.** The standard transform layer, with lineage, tests and
  docs. Rejected for M3 because its hardest work would be its least readable
  part; kept for M5, where its strengths fit.
- **Matching places with a geocoding service or an LLM.** Rejected: network
  calls in a transform, results that change between runs, and guesses that
  can't be traced to a rule.
